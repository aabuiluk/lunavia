Організація практики

Структура команди та робочий процес, максимально наближений до реального проєкту.

Команди

КНК-41 — 16 студентів. Формуємо дві приблизно рівні за силою команди по 8 осіб.

  • сильніших студентів рівномірно розподіляємо між командами;
  • у кожній команді один із сильніших студентів допомагає з лідством;
  • лідерство не звільняє від frontend, backend або QA задач.

Інструменти

Кожна команда працює як окремий невеликий delivery team.

  • окремий Jira-проєкт: 8 студентів + викладач;
  • спільний Slack для всіх 16 студентів;
  • Git + branches + Pull Requests + code review;
  • React, FastAPI, PostgreSQL, Swagger/OpenAPI, CI/CD.
Спільна база + спеціалізація. Frontend проходять усі студенти приблизно в однаковому обсязі. Частина студентів обирає Design Track і значно глибше працює з візуальним дизайном, UX/UI та реалізацією дизайну у React. Інша частина обирає Programming Track і значно глибше працює з FastAPI, бізнес-логікою, базою даних та інтеграцією. Орієнтир: дизайнери отримують приблизно ×3 більше design-задач, програмісти — приблизно ×3 більше backend-задач. Frontend залишається спільною частиною для всіх.

Design Track — Visual Design + Frontend

Для студентів, які хочуть більше зануритися у візуальну частину продукту.

  • Frontend: такий самий базовий обсяг, як у всіх;
  • Design: ≈ ×3 більше практики — Figma, UI kit, typography, layout, responsive design, component states, UX/UI review;
  • Backend: базове знайомство та прості API/integration tasks для розуміння повного циклу.

Programming Track — Backend + Frontend

Для студентів, які хочуть більше зануритися у програмування та серверну частину.

  • Frontend: такий самий базовий обсяг, як у всіх;
  • Backend: ≈ ×3 більше практики — FastAPI, CRUD, validation, DB, business logic, API integration;
  • Design: базова участь у Design Review та робота за узгодженими макетами.

Cross-team QA

Мета: протестувати продукт «чужими очима» та знайти реальні дефекти.
21 вересня
Формат
  • Team A тестує Team B;
  • Team B тестує Team A;
  • не підказуємо, як «мало б працювати»;
  • тестуємо deployed version.
Що тестуємо
  • основний user flow;
  • forms;
  • negative cases;
  • API;
  • UI/UX.
Bug Reports
  • summary;
  • steps;
  • actual/expected;
  • environment;
  • severity/priority.
Якість
  • bug має бути відтворюваним;
  • додаємо screenshot/log за потреби;
  • не створюємо дублікати;
  • усе фіксуємо в Jira.
До кінця дня: кожна команда отримує структурований набір дефектів і розуміє, що критично виправити до release.

Bug Fixing

Мета: навчитися працювати не з новою feature, а з дефектом і ризиком regression.
22 вересня
Triage
  • Critical/High/Medium/Low;
  • визначаємо пріоритет;
  • призначаємо owner;
  • відкидаємо duplicate/not a bug.
Fix
  • відтворити bug;
  • знайти root cause;
  • внести мінімальну зміну;
  • локально перевірити fix.
Git workflow
  • окрема branch;
  • PR;
  • code review;
  • посилання на Jira bug;
  • merge та deploy.
Правило
  • автор fix не закриває bug сам;
  • retest робить інший студент;
  • якщо defect лишився — Reopen;
  • critical bugs мають пріоритет над косметикою.
До кінця дня: critical/high bugs або виправлені, або мають чіткий план і owner.

Retest + Regression

Мета: довести, що виправлення працює і не зламало інші сценарії.
23 вересня
Retest
  • повторюємо steps;
  • перевіряємо deployed build;
  • закриваємо або reopen bug;
  • фіксуємо результат.
Regression
  • critical user flows;
  • auth/CRUD/search — залежно від продукту;
  • API;
  • frontend-backend integration.
Code cleanup
  • debug logs;
  • dead code;
  • hardcoded URLs;
  • очевидне дублювання;
  • небезпечні secrets.
Release decision
  • які bugs блокують release;
  • які можна залишити як known issues;
  • що більше не чіпаємо;
  • чи готові до Feature Freeze.
До кінця дня: є зрозумілий release status та підтверджена стабільність основного функціоналу.

Release Candidate + Demo Preparation

Мета: зафіксувати продукт і підготувати команду до професійної презентації.
24 вересня
Feature Freeze
  • нових features немає;
  • тільки blockers;
  • final regression;
  • final deploy.
README
  • project description;
  • stack;
  • local run;
  • env;
  • DB/API/Swagger;
  • known limitations.
Presentation
  • розподіляємо частини між 8 студентами;
  • готуємо live demo;
  • показуємо не тільки UI, а й процес;
  • репетиція Q&A.
Що показуємо
  • Problem;
  • Design;
  • Frontend;
  • Backend/DB;
  • Swagger;
  • QA/bugs;
  • CI/CD.
До кінця дня: є Release Candidate, актуальний README, стабільний deploy та відрепетирувана командна презентація.

Final Demo Day

Мета: презентувати результат, пояснити технічні рішення та підвести підсумки практики.
25 вересня
Формат
  • приблизно 20 хв demo;
  • до 10 хв Q&A;
  • обидві команди присутні;
  • виступає кожен студент.
Презентація
  • проблема та MVP;
  • архітектура;
  • React;
  • FastAPI/PostgreSQL;
  • Swagger;
  • QA та bugs.
Live Demo
  • працюємо з deployed version;
  • показуємо основний user flow;
  • не ховаємо known limitations;
  • відповідаємо на технічні питання.
Retrospective
  • що спрацювало;
  • що було складно;
  • що зробили б інакше;
  • які навички кожен забирає з практики.
Фінальний результат: студенти показують не лише готовий сайт, а весь цикл роботи — від planning до release і QA.

Правила використання AI

AI залишається інструментом і ментором, але не виконує Jira task замість студента.

Можна

  • пояснювати концепції та помилки;
  • розбирати stack trace;
  • допомагати знайти причину bug;
  • пояснювати документацію;
  • проводити code review;
  • використовувати autocomplete для невеликих фрагментів.

Не можна

  • «зроби всю React-сторінку»;
  • «реалізуй цей Jira ticket»;
  • «створи весь backend»;
  • «згенеруй усі test cases»;
  • «ось репозиторій — дороби все»;
  • «виправ усі bugs у проєкті».
Якщо студент не може пояснити код зі свого Pull Request на review — задача повертається в In Progress, навіть якщо код формально працює.
